    9. Asynchronous Programming

    The previous chapter introduced threads: we can execute multiple pieces of code “at the same time,” synchronize them, and assign tasks to a thread pool via an executor ([ExecutorService]). This chapter addresses a related but distinct issue: how to write a program that waits a lot (for the disk, the network, or a database) without tying up threads during these waits.

    Java does not have language keywords for this (other languages, such as C# or JavaScript, have the keywords [async] and [await]). It offers two solutions, which complement each other and are both presented in this chapter:

    • the [CompletableFuture<T>] class (Java 8, since enhanced) represents an ongoing operation whose subsequent steps are composed using callback methods: “when the result is ready, do this, then that” ([thenApply], [thenCompose], [thenCombine], [allOf]…). No thread waits: it is the completion of the operation that triggers the next step;
    • virtual threads ( Java 21), on the other hand, allow you to write blocking, sequential code that reads from top to bottom: when a virtual thread waits for input/output, the JVM detaches it from the system thread that was executing it (its “carrier thread”) and frees that thread for another virtual thread. This makes it possible to have hundreds of thousands of virtual threads for just a few system threads. This is Java’s modern solution to the problem that other languages solve with [async] / [await].

    These tools are everywhere today: the following chapters will explore them to access databases, write TCP servers that serve each client via a virtual thread, web clients using [java.net.http.HttpClient], and web services using Spring Boot.

    All the examples in this chapter are compact source files ([Async01.java], [Async02.java]…) that are run using [java AsyncNN.java] in the [09-async] folder. Many of them measure execution times using [System.nanoTime()]: the milliseconds displayed vary from one run to another and from one machine to another (the examples were run on a dual-processor machine). It’s the orders of magnitude that matter: 1 second or 10 seconds, 300 ms or 0 ms.

    9.1. Why Asynchrony

    9.1.1. Operations that wait

    A program performs two types of work:

    • computational tasks, which occupy the processor: sorting a list, calculating a tax, analyzing a text;
    • input/output (I/O), which essentially consists of waiting for a peripheral device: reading a file from disk, sending a request to a web server and waiting for its response, executing a SQL query on a database server.

    The orders of magnitude are very different. A processor executes a few billion instructions per second. A read operation on a disk (SSD) takes on the order of one-tenth of a millisecond; a round trip over a local network takes a fraction of a millisecond; a round trip to a server located on the other side of the country takes a few tens of milliseconds; and a somewhat complex SQL request can sometimes take several seconds. During these waits, the processor could have executed millions of instructions.

    When a program reads a line over a network connection using a blocking method, the thread performing this read is blocked: it does nothing, but it still exists. A “classic” Java thread—now referred to as a “platform thread”—is an operating system thread: it occupies memory (its stack, on the order of a megabyte), it is recognized by the system, and, most importantly, it is no longer available to do anything else. This isn’t a problem in a small console program that does one thing at a time. It becomes much more of an issue in two situations:

    • in a server: each client served by a blocked thread ties up that thread. If the server’s thread pool has N threads and all N threads are performing a blocking operation, there are no threads left available for a new client. A modern server handles thousands of simultaneous requests: this is possible because its waiting operations do not tie up system threads;
    • in a graphical user interface: a single thread—the UI thread (Swing’s “Event Dispatch Thread,” the “JavaFX Application Thread”)—handles clicks and redraws windows. If it is blocked by a download, the window freezes.

    Asynchrony involves initiating the I/O operation, freeing up the system thread while it is in progress (the hardware and operating system do not need it to transfer data), and then resuming work once the operation is complete, possibly on another system thread:

    • In [1], the platform thread T1 initiates the I/O and remains blocked until it finishes;
    • in [2], the virtual thread V1 initiates the I/O; JVM detaches it from its parent thread P1, which can then immediately execute other virtual threads. When the I/O completes, JVM reattaches V1 to a free carrier thread, P2 (which could also be P1), and V1 continues its execution immediately after the blocking instruction, as if nothing had happened.

It uses instructions that we will explain later in this chapter ([Executors.newVirtualThreadPerTaskExecutor], [CompletableFuture]): here, we are primarily interested in the results.

    // Why asynchrony: 100 operations, each waiting one second
// (a wait simulates I/O: disk read, network request, SQL request…)
import java.lang.management.ManagementFactory;

final int nbOperations = 100;
long debut;

void main() throws InterruptedException {
    IO.println(nbOperations + " opérations d'une seconde, "
            + Runtime.getRuntime().availableProcessors() + " processeurs");

     // 1 - one platform thread per operation; each thread is blocked during the wait
    debut = System.nanoTime();
    List<Thread> threads = new ArrayList<>();
    for (int i = 0; i < nbOperations; i++) {
        threads.add(Thread.ofPlatform().start(() -> attendre(1000)));
    }
    afficher("1 - un thread de plate-forme par opération", threadsDeLaJvm());
    for (Thread thread : threads) {
        thread.join();
    }
    afficher("    fin", -1);

     // 2 - operations are assigned to a pool of 10 threads, but they block the pool
    debut = System.nanoTime();
    try (ExecutorService pool = Executors.newFixedThreadPool(10)) {
        for (int i = 0; i < nbOperations; i++) {
            pool.submit(() -> attendre(1000));
        }
        afficher("2 - pool de 10 threads, attentes bloquantes", threadsDeLaJvm());
    } // `close()` waits for all operations to complete
    afficher("    fin", -1);

     // 3 - one virtual thread per operation: it releases its host thread while waiting
    debut = System.nanoTime();
    try (ExecutorService executeur = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < nbOperations; i++) {
            executeur.submit(() -> attendre(1000));
        }
        afficher("3 - un thread virtuel par opération", threadsDeLaJvm());
    }
    afficher("    fin", -1);

     // 4 - Asynchronous waits: no thread waits; a timer completes each operation
    debut = System.nanoTime();
    var operations = new CompletableFuture<?>[nbOperations];
    for (int i = 0; i < nbOperations; i++) {
        operations[i] = new CompletableFuture<Void>().completeOnTimeout(null, 1000, TimeUnit.MILLISECONDS);
    }
    afficher("4 - attentes asynchrones (CompletableFuture)", threadsDeLaJvm());
    CompletableFuture.allOf(operations).join();
    afficher("    fin", -1);
}

// a blocking wait of [ms] milliseconds
void attendre(long ms) {
    try {
        Thread.sleep(ms);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}

// number of platform threads for JVM, half a second after operations begin
int threadsDeLaJvm() {
    long ecoule = (System.nanoTime() - debut) / 1_000_000;
    if (ecoule < 500) {
        attendre(500 - ecoule);
    }
    return ManagementFactory.getThreadMXBean().getThreadCount();
}

// displays the elapsed time and, if provided (>= 0), the number of threads
void afficher(String message, int nbThreads) {
    String infoThreads = nbThreads < 0 ? "" : String.format(", %3d threads dans la JVM", nbThreads);
    long ecoule = (System.nanoTime() - debut) / 1_000_000;
    IO.println(String.format("%-44s : %5d ms%s", message, ecoule, infoThreads));
}

    • Lines 12–22: the simplest solution—one platform thread per operation. [Thread.ofPlatform().start(tâche)] (Java 21) creates and starts a thread, just like [new Thread(tâche).start()]. Each thread executes [Thread.sleep(1000)]: it is blocked for one second. The 100 waits occur simultaneously, and the entire process takes exactly one second (line 4 of the results), but at the cost of 100 additional system threads: JVM has 106 of them (line 3). With 10,000 operations, 10,000 system threads would be required;
    • Lines 24–32: The operations are assigned to a pool of 10 threads ([Executors.newFixedThreadPool(10)]), a reasonable size for computations. But here, these threads aren’t computing—they’re idle. The operations wait for a free thread, in batches of 10, and the whole process takes… ten seconds (line 6). This is known as “thread pool starvation,” the most common flaw in servers that mix thread pools with blocking I/O. The method [close()] of an executor (Java 19), called upon exit from [try], rejects new tasks and waits for the ones that have been submitted to finish;
    • Lines 34–42: One virtual thread per operation. [Executors.newVirtualThreadPerTaskExecutor()] (Java 21) returns an executor that creates a new virtual thread for each submitted task. The task code is the same as in Step 1: a blocking [Thread.sleep(1000)]. However, a blocked virtual thread does not tie up a system thread: the JVM detaches it from its carrier thread. The 100 waits last a total of one second (line 8), and the JVM counts only 10 system threads (line 7): its service threads, and the two carrier threads—one per processor—that executed the 100 virtual threads. The virtual threads are not included in this count: they are objects of JVM, not system threads;
    • lines 44–52: the same wait with no threads waiting. [new CompletableFuture<Void>()] creates a “pending” operation, and [completeOnTimeout(valeur, délai, unité)] (Java 9) requests that it be completed with the specified value once the timeout expires. A single timer from JVM manages the 100 timeouts. [CompletableFuture.allOf(...)] returns an operation that completes when all others have finished, and [join()] waits for it to finish. The entire process lasts one second (line 10), with only one additional thread compared to step 3—the timer thread (line 9);
    • lines 55–62: [Thread.sleep] can throw the controlled exception [InterruptedException] if the thread is interrupted while sleeping (we’ll discuss this further in the section on cancellation); the [attendre] method intercepts it so that the lambdas on lines 16, 28, and 38 do not have to handle it;
    • Lines 64–71: [ManagementFactory.getThreadMXBean().getThreadCount()] returns the number of live platform threads for JVM. The class [ManagementFactory] belongs to the module [java.management]: a compact source file automatically imports only the module [java.base], hence the import on line 3.

    Let’s remember the lesson: to wait, you must not block any system threads. Asynchrony doesn’t make I/O faster; it allows you to handle a large number of I/O operations simultaneously using few system threads, while keeping the threads the application needs available. Java offers two approaches for this: creating [CompletableFuture] (Step 4), or writing ordinary blocking code executed by virtual threads (Step 3).

    9.1.2. Several Successive Models

    Java has offered several ways to write code that waits without blocking. The older ones are still found in existing code, so it’s useful to recognize them.

    Pattern
    Introduction
    Principle
    [Future] and Runtimes
    Java 5 (2004)
    [ExecutorService.submit] assigns a task to a thread pool and returns a [Future<T>], which represents the upcoming result. But the only way to obtain this result is to wait, blocking, with [get()].
    Callback methods of NIO.2
    Java 7 (2011)
    Asynchronous channels ([AsynchronousSocketChannel], [AsynchronousFileChannel]) initiate an operation and receive a callback object ([CompletionHandler]) whose method [completed] or [failed] is called by a thread from a pool once the operation is complete.
    [CompletableFuture]
    Java 8 (2014)
    a [Future] that you can terminate yourself and whose sequence is composed of callback methods ([thenApply], [thenCompose], [exceptionally]…); reactive streams [java.util.concurrent.Flow] (Java 9) are an extension of this for sequences of values. Reactive libraries (Project Reactor, used by Spring WebFlux, RxJava) are based on the same concepts.
    virtual threads
    Java 21 (2023)
    of ordinary blocking code, executed by virtual threads: JVM frees the system thread during waits. This is the recommended model today for new applications.
    structured concurrency
    Preview of Java 21 through Java 25
    [StructuredTaskScope] organizes a group of subtasks executed by virtual threads as a single block of code, with shared error handling and cancellation (see the end of the chapter).

    Callback methods have a drawback: the code is fragmented. What naturally reads as “connect, then read, then display” becomes a method that initiates the connection, a callback method that initiates the read operation, and another callback method that displays the result; variables must be shared among these methods, exceptions are caught at different locations, and a simple loop (“read as long as there is data”) becomes a callback method that recursively calls itself. [CompletableFuture] makes this fragmentation more readable by chaining the steps together; virtual threads make it disappear: asynchronous code takes the form of synchronous code, because it is synchronous code.

    // the same client, TCP, written using callback methods (NIO.2, Java 7), then with a virtual thread (Java 21)
final int port = 27500;
final InetAddress local = InetAddress.getLoopbackAddress();
final ByteBuffer tampon = ByteBuffer.allocate(1024);
final CountDownLatch fin = new CountDownLatch(1);

void main() throws IOException, InterruptedException {
     // a minimal server, run by a single thread: it serves two clients and then stops
    var ecoute = new ServerSocket(port, 10, local);
    Thread serveur = Thread.ofPlatform().name("serveur").start(() -> {
        try (ecoute) {
            for (int i = 1; i <= 2; i++) {
                try (Socket service = ecoute.accept()) {
                     // the server takes its time to respond
                    Thread.sleep(500);
                    byte[] message = ("Bonjour client n° " + i).getBytes(StandardCharsets.UTF_8);
                    service.getOutputStream().write(message);
                }
            }
        } catch (IOException | InterruptedException e) {
            afficher("serveur : " + e);
        }
    });
    afficher("début du programme");

     // 1 - the “callback methods” style: AsynchronousSocketChannel and CompletionHandler
    var client = AsynchronousSocketChannel.open();
     // The connection is initiated by specifying the object to be called back once the connection is established
    client.connect(new InetSocketAddress(local, port), client, new Connecte());
    afficher("rappels : connexion lancée, le programme continue");
     // The main thread has nothing left to do: it waits for the signal from the last callback method
    fin.await();

     // 2 - The blocking style, executed by a virtual thread: the code is read from top to bottom
    Thread virtuel = Thread.ofVirtual().start(() -> {
        try (var client2 = new Socket(local, port)) {
            afficher("thread virtuel : connecté, lecture lancée");
            byte[] octets = new byte[1024];
            int nbOctets = client2.getInputStream().read(octets);
            String message = new String(octets, 0, nbOctets, StandardCharsets.UTF_8);
            afficher("thread virtuel : reçu [" + message + "]");
        } catch (IOException e) {
            afficher("thread virtuel : " + e);
        }
    });
    virtuel.join();
    serveur.join();
}

// Callback method #1: the connection is established (or has failed)
class Connecte implements CompletionHandler<Void, AsynchronousSocketChannel> {
    @Override
    public void completed(Void rien, AsynchronousSocketChannel canal) {
        afficher("rappels : connecté, lecture lancée");
         // We start reading the server’s response using another callback object
        canal.read(tampon, canal, new Recu());
    }

    @Override
    public void failed(Throwable e, AsynchronousSocketChannel canal) {
        afficher("rappels : échec de la connexion : " + e);
        fin.countDown();
    }
}

// Callback method #2: data has arrived
class Recu implements CompletionHandler<Integer, AsynchronousSocketChannel> {
    @Override
    public void completed(Integer nbOctets, AsynchronousSocketChannel canal) {
        afficher("rappels : reçu [" + new String(tampon.array(), 0, nbOctets, StandardCharsets.UTF_8) + "]");
        try {
            canal.close();
        } catch (IOException e) {
            afficher("rappels : " + e);
        }
         // Notify the main thread
        fin.countDown();
    }

    @Override
    public void failed(Throwable e, AsynchronousSocketChannel canal) {
        afficher("rappels : échec de la lecture : " + e);
        fin.countDown();
    }
}

// (name of a platform thread, description of a virtual thread)
void afficher(String message) {
    Thread thread = Thread.currentThread();
    IO.println("[" + (thread.isVirtual() ? thread.toString() : thread.getName()) + "] " + message);
}

    9.2. Upcoming tasks: Future and CompletableFuture

    A [Future<T>] (interface of the [java.util.concurrent] package, Java 5) is an object that represents the result—of type [T]—of an ongoing or completed operation. We encountered it in the previous chapter: this is what the [submit] method of an executor returns. You can query it (has it finished? was it successful?), cancel it ([cancel]), and wait for its result ([get]), but nothing else: the only way to use the result is to block a thread until it is available.

    The [CompletableFuture<T>] class (Java 8) implements [Future<T>] and adds two essential capabilities:

    • you can terminate it yourself, with a result ([complete]) or an exception ([completeExceptionally]);
    • you can attach a follow-up operation to it—a function that will be executed when the result is available ([thenApply], [thenAccept], [thenCompose]…), which produces a new [CompletableFuture]. In this way, chains of operations are constructed without any threads having to wait. These methods are declared by the [CompletionStage<T>] interface, which [CompletableFuture] also implements.

    A [CompletableFuture] is not a thread. It may represent a process executed by a thread of an executor (as is the case with those created by [supplyAsync]), but many are not executed by any thread: the one in step 4 of [Async01.java] is simply “completed” by a timer after one second, and the one returned by [HttpClient.sendAsync] is completed when the server’s response arrives. It is a promise of a result.

    9.3. Asynchronous methods

    9.3.1. First approach: returning a CompletableFuture

    In Java, an asynchronous method is simply a method that initiates an operation and immediately returns, without waiting, a [CompletableFuture] that represents it:

    • [CompletableFuture<Void>] if the operation returns no result;

    The language does not impose any naming conventions. Java libraries often suffix these methods with [Async] ([sendAsync], [supplyAsync]), but this is not a rule: the return type is sufficient to identify them.

    9.3.3. What JVM Does

    How can a virtual thread be interrupted in the middle of a loop, release its host thread, and then resume later at the same point, with the same local variable values, possibly on a different host thread? A virtual thread is a Java object ([java.lang.VirtualThread], a class derived from [Thread]) that has its own call stack. To execute it, JVM “mounts” it onto a carrier thread—a platform thread of a [ForkJoinPool] reserved for this purpose, which by default has as many threads as there are processors. When the virtual thread calls a blocking operation ([Thread.sleep], reading from a socket; [BlockingQueue.take], waiting for a lock…), the classes in JVM—rewritten for this purpose in Java 21—do not block the containing thread:

    • they register the operation with the system (a timer for a delay, the system’s I/O notification mechanism—[epoll] on Linux—for a socket);
    • they “unmount” the virtual thread: its call stack frames are copied to the heap as an object called a continuation, and the carrier thread is returned to [ForkJoinPool], which assigns it another virtual thread ready to execute;
    • when the operation completes, the virtual thread becomes ready again: it will be remounted onto the first available carrier thread, its stack frames will be recopied, and execution will resume immediately after the blocking call.

    This is the principle behind callback methods (“call me back when the operation is complete”), but it is the JVM that breaks down the execution, saves the variables, and restores the context at the call stack level, without the source code showing any trace of it. Other languages entrust this task to the compiler, which transforms each [async] method into a “state machine”; Java entrusts it to the JVM, which allows it to handle all existing code in the same way.

    There are two limitations to be aware of:

    • certain operations cannot detach the virtual thread; it therefore remains “pinned” to its host thread, which is blocked while waiting. This occurs during the execution of a native method, and during most file reads and writes (the system does not provide a notification for files that can be used by the JVM); for the latter, the [ForkJoinPool] compensates by temporarily creating an additional carrier thread. Up to Java 23, this was also the case for a virtual thread waiting inside a [synchronized] block; since Java 24, this is no longer the case;
    • a virtual thread does not speed up a computation: a virtual thread performing a computation occupies its host thread for the entire duration of the computation. Virtual threads are intended for programs that do a lot of waiting, not those that do a lot of computation (for the latter, thread pools and parallel streams from the previous chapter are available).

While one is sleeping, its carrier thread is free for the other. Therefore, in a virtual thread, one must never assume that the code following a wait is executed by the same carrier thread as the code preceding it; but it is always the same virtual thread, and that is what matters to the program ([Thread.currentThread()] returns the virtual thread; its variables, [ThreadLocal], are preserved).

    This method of performing multiple operations simultaneously without increasing the number of system threads is called concurrency. It differs from parallelism, which involves executing multiple calculations at the same time across multiple processors (as discussed in the previous chapter: thread pools, parallel streams). Asynchrony facilitates I/O concurrency; it does not make calculations faster.

    The choice of executor is therefore important:

    • the shared pool is suitable for brief continuations and short computations; blocking operations should not be executed there, as this risks the starvation described in [Async01.java] (it has only one thread on our machine);
    • for a blocking operation (I/O, calls to JDBC or [Thread.sleep]), use a virtual thread executor: [CompletableFuture.supplyAsync(fournisseur, executeurVirtuel)];
    • for a graphical user interface, we pass an executor that has the continuation executed by the UI thread, which allows the graphical components to be updated: with Swing, [thenAcceptAsync(action, SwingUtilities::invokeLater)] (the method reference [SwingUtilities::invokeLater] is a valid [Executor], since [Executor] is a functional interface whose sole method takes a [Runnable]); with JavaFX, [Platform::runLater].

    9.6. Cancellation and Deadlines

    9.6.1. Future.cancel and thread termination

    A long-running operation must be able to be canceled: the user clicked on [Annuler], a server client disconnected, the application shut down, or a timeout occurred. Java uses a cooperative mechanism for this—thread interruption:

    • a thread’s [interrupt()] method sets its interrupt flag; it does not stop the thread (the [Thread.stop] method, which forced a stop, has been deprecated since Java 20: it calls [UnsupportedOperationException]);
    • if the thread is blocked in an interruptible wait ([Thread.sleep], [Object.wait], [Thread.join], [BlockingQueue.take], [Future.get]…), the wait is immediately interrupted and triggers a [InterruptedException], clearing the flag;
    • a thread that performs calculations checks its own indicator regularly using [Thread.currentThread().isInterrupted()] and terminates gracefully if it is set;
    • the [cancel(true)] method of a [Future] returned by an executor transitions the task to the [CANCELLED] state and interrupts the thread executing it ([cancel(false)] simply prevents the task from starting if it has not yet done so). After cancellation, [get()] launches a [CancellationException].

    The mechanism is cooperative: no one forcibly stops an operation; the operation stops itself at a point where it can do so cleanly. This is why a method that intercepts a [InterruptedException] must not ignore it: it must either propagate it, terminate itself, or at the very least reset the flag with [Thread.currentThread().interrupt()] so that the calling code knows that an interruption has been requested (this is what our method [dormir] does).

// reads an entire (small) file using a AsynchronousFileChannel
CompletableFuture<String> lireAsynchrone(Path fichier) {
    CompletableFuture<String> resultat = new CompletableFuture<>();
    try {
        AsynchronousFileChannel canal = AsynchronousFileChannel.open(fichier, StandardOpenOption.READ);
        ByteBuffer tampon = ByteBuffer.allocate((int) canal.size());
         // Reading begins; the callback object will terminate the CompletableFuture
        canal.read(tampon, 0, tampon, new CompletionHandler<Integer, ByteBuffer>() {
            @Override
            public void completed(Integer nbOctets, ByteBuffer lus) {
                resultat.complete(new String(lus.array(), 0, nbOctets, StandardCharsets.UTF_8));
            }

            @Override
            public void failed(Throwable e, ByteBuffer lus) {
                resultat.completeExceptionally(e);
            }
        });
         // the channel will be closed when reading is complete, regardless of the outcome
        resultat.whenComplete((texte, e) -> fermer(canal));
    } catch (IOException e) {
        resultat.completeExceptionally(e);
    }
    return resultat;
}

    9.9. Asynchronous Value Streams

    An asynchronous operation returns a result after a certain amount of time. A stream ([Stream]) or an iterator returns a sequence of values, produced on demand. Sometimes it is necessary to combine the two: a sequence of values where each one requires a wait before being produced. This is the case for lines in a large file, the rows in the result of a query SQL, messages arriving over a network connection, sensor readings… Other languages have a dedicated type for this; Java offers two models:

    • the “pull” model: the consumer requests the next value and waits for it to be available. With virtual threads, this is simply a [Iterator] or a [Stream] where the production of each value blocks, read by a virtual thread;
    • the “push” model: the producer sends values to its subscribers as they are produced, and the subscribers control the throughput. This is the reactive stream model, standardized by the [java.util.concurrent.Flow] interfaces (Java 9).

    9.9.2. The push model: Flow and SubmissionPublisher

    The [java.util.concurrent.Flow] interface (Java 9) groups together four internal interfaces that standardize reactive streams:

    • [Flow.Publisher<T>], the publisher, produces values; its method [subscribe] adds a subscriber to it;
    • [Flow.Subscriber<T>], the subscriber, receives values via its method [onNext], the end of the stream via [onComplete], an error via [onError], and at the beginning, the object [Flow.Subscription], which links it to the publisher via [onSubscribe];
    • [Flow.Subscription], the subscription: [request(n)] requests additional values from [n], and [cancel()] terminates the subscription. The publisher never sends more values than the subscriber has requested: this is “backpressure,” which prevents a fast publisher from overwhelming a slow subscriber;
    • [Flow.Processor<T, R>] is both a subscriber and a publisher (a transformation node).

    Java provides an implementation of the publisher, [SubmissionPublisher<T>], which delivers values to each subscriber via an executor and a buffer specific to that subscriber. Reactive libraries (Project Reactor, RxJava) implement these same interfaces and add dozens of operators to them.     private final String nom;
    private final long duree;
    private final double seuil;
    private Flow.Subscription abonnement;

        this.nom = nom;
        this.duree = duree;
        this.seuil = seuil;
    }

    @Override
    public void onSubscribe(Flow.Subscription abonnement) {
        this.abonnement = abonnement;
         // The subscriber requests the values one by one: the subscriber controls the data rate
        abonnement.request(1);
    }

    @Override
    public void onNext(Mesure mesure) {
        afficher("  " + nom + " : reçu " + mesure);

            abonnement.request(1);

    @Override
    public void onError(Throwable e) {
        afficher("  " + nom + " : erreur " + e);
        fin.countDown();
    }

    @Override
    public void onComplete() {
        afficher("  " + nom + " : fin du flux");
        fin.countDown();
    }
}

    9.10.1. A cache for asynchronous operations

    A [CompletableFuture] is an object: each call to a method that returns one allocates at least one object on the heap, which the garbage collector must reclaim.          // If the currency is in the cache, the existing CompletableFuture is returned: no object is created
        return cache.computeIfAbsent(code, this::lireTauxServeur);

        nbAccesServeur.incrementAndGet();

            if (e != null) {
                cache.remove(code);
            }
        });

    }

    int nbLectures() {
        return nbLectures.get();
    }

    Set<String> devisesEnCache() {
        return new TreeSet<>(cache.keySet());
    }

    9.10.2. Return to the GUI thread

    The program [Async06.java] demonstrated that a continuation is executed, depending on the case, either by the thread that completes the operation or by a thread of the selected executor. In a graphical application (Swing, JavaFX), this matters: a graphical component can only be manipulated by the UI thread. Java has no mechanism that automatically returns the rest of the code to this thread; it is up to the program to request this, either by passing the correct executor to the continuation or by using the tools of the graphics library:

    • with Swing, *[SwingUtilities.invokeLater(action)] causes the action to be executed by the interface thread; the method reference [SwingUtilities::invokeLater] can serve as an executor for a continuation: [telechargement.thenAcceptAsync(page -> zoneTexte.setText(page),*** ***SwingUtilities::invokeLater)]. The [SwingWorker] class also provides a method, [doInBackground], which is executed by a background thread, and methods [process] and [done]*, which are executed by the interface’s thread;
    • along with JavaFX, [Platform.runLater(action)] serves the same purpose, and the classes [Task] and [Service] of [javafx.concurrent] encapsulate a background process along with its progress.

    In all cases, the rule is the same: the UI thread must never wait ([join()], [get()], blocking I/O), otherwise the window freezes. The long-running task is executed by another thread (a virtual thread, for example), and only the final update of the components is handled by the interface thread.

// converts the thermometer’s notifications into a CompletableFuture
CompletableFuture<Double> attendreTemperature(Thermometre thermometre, double seuil) {
     // a CompletableFuture that you will terminate yourself
    CompletableFuture<Double> resultat = new CompletableFuture<>();
     // the listener terminates the QZXW2HTMLCQ9tcGxldGFibGVGdXR1cmUZQX when the threshold is reached
    DoubleConsumer ecouteur = temperature -> {
        if (temperature >= seuil) {
            resultat.complete(temperature);
        }
    };
    thermometre.ajouterEcouteur(ecouteur);
     // regardless of how it ends (threshold, timeout, cancellation), the listener is removed
    resultat.whenComplete((temperature, e) -> thermometre.retirerEcouteur(ecouteur));
     // The CompletableFuture is returned immediately; it will be terminated later
    return resultat;
}

    9.11.1. Virtual threads and semaphores

final AtomicInteger enCours = new AtomicInteger();

void main() {
    debut = System.nanoTime();
    List<String> pages = IntStream.rangeClosed(1, 9).mapToObj(i -> "page" + i + ".html").toList();
     // No more than 3 downloads at the same time: a semaphore with 3 permissions

        for (String page : pages) {

                try {

                } finally {

                }
                return null;
            });
        }

}

    9.11.2. Producers / Consumers: BlockingQueue

    The previous chapter introduced the producer/consumer model: producers place items into a queue, and consumers remove them. // the producer: one order every 50 ms
Void produire(int nbCommandes) throws InterruptedException {
    for (int i = 1; i <= nbCommandes; i++) {
        Thread.sleep(50);
         // The producer places the order immediately if there is space in the queue
        if (file.offer(i)) {
            afficher("P  : commande " + i + " déposée");
        } else {
             // Queue full: the producer waits until a spot becomes available
            afficher("P  : file pleine, la commande " + i + " attend");
            file.put(i);
            afficher("P  : commande " + i + " déposée");
        }
    }
     // nothing more will be produced: the end token is placed
    file.put(FIN);
    afficher("P  : fin de la production");
    return null;
}

// A consumer: processing an order takes 400 ms
Void consommer(String nom) throws InterruptedException {
    while (true) {
         // take waits until there is an order in the queue
        int commande = file.take();
        if (commande == FIN) {
             // The end marker is placed back in the queue for the other consumer
            file.put(FIN);
            break;
        }
        afficher(nom + " : traitement de la commande " + commande);
        Thread.sleep(400);
    }
    afficher(nom + " : plus de commandes");
    return null;
}

    9.12. Time: ScheduledExecutorService and Clock

    Two tools complement those related to time:

    • a [ScheduledExecutorService] (Java 5) is an executor capable of running a task after a delay ([schedule]) or periodically ([scheduleAtFixedRate], at fixed intervals measured from the start of one execution to the next; [scheduleWithFixedDelay], with a fixed delay between the end of one execution and the start of the next). A periodic task is never executed twice at the same time: if an execution takes longer than the period, the next one is delayed. A single-threaded executor is obtained with [Executors.newSingleThreadScheduledExecutor()];
    • the abstract class [java.time.Clock] (Java 8) represents the clock: it provides the current time and time zone. [Clock.systemDefaultZone()] is the system clock in the machine’s time zone. All [now()] methods of API, [java.time] ([LocalDateTime.now(horloge)], [Instant.now(horloge)]…) accept a clock. A class that depends on the time receives a [Clock] instead of calling [LocalDateTime.now()]: it can then be tested with a controlled clock.

    9.13. Structured Concurrency (Overview)

    In the previous examples, the operations launched by a program run independently of it: if one fails, the others continue; if the code that launched them is interrupted, they continue as well; and nothing forces that code to wait for them to finish. Structured concurrency proposes treating a group of subtasks as a single block: they are launched within a scope, the scope waits for them to complete, and if one fails, the others are canceled. The [StructuredTaskScope] class implements this idea using virtual threads. It has been available since Java 21 but is still in “preview” status in Java 25: its API may still change, and a program that uses it must be compiled and run with the [--enable-preview] option.         portee.fork(() -> lireTemperature("miroir-lyon", 300));

static final Pattern CONTRIBUABLE = Pattern.compile("([on])\\s+(\\d+)\\s+(\\d+)");

void main() {
    Path resultats = Path.of("resultats.txt");
    try (ExecutorService executeur = Executors.newVirtualThreadPerTaskExecutor()) {
         // Both input files are read simultaneously by two virtual threads
        Future<List<TrancheImpot>> lectureTranches = executeur.submit(
                () -> chargerTranches(Path.of("DataImpot.txt")));
        Future<List<String>> lectureContribuables = executeur.submit(
                () -> Files.readAllLines(Path.of("contribuables.txt")));
         // the calculation waits for both files to be read, then writes the results
        Future<Integer> traitement = executeur.submit(
                () -> calculerImpots(lectureTranches.get(), lectureContribuables.get(), resultats));
        try {
             // The entire process is limited to 10 seconds
            int nbResultats = traitement.get(10, TimeUnit.SECONDS);
            IO.println(nbResultats + " lignes écrites dans [" + resultats + "] :");
            IO.print(Files.readString(resultats));
        } catch (TimeoutException e) {
            traitement.cancel(true);
            IO.println("traitement abandonné : délai dépassé");
        }
    } catch (ExecutionException e) {
         // An error in one read operation is wrapped twice: by the read operation itself and by the calculation that was waiting for it
        Throwable cause = e.getCause();
        while (cause instanceof ExecutionException) {
            cause = cause.getCause();
        }
        IO.println("erreur : " + cause.getClass().getSimpleName() + " : " + cause.getMessage());
    } catch (IOException | InterruptedException e) {
        IO.println("erreur : " + e.getClass().getSimpleName() + " : " + e.getMessage());
    }
}

// reads the tax brackets (range: coeffR:coeffN, decimal point)
List<TrancheImpot> chargerTranches(Path fichier) throws IOException {
    try (Stream<String> lignes = Files.lines(fichier)) {
        return lignes.filter(ligne -> !ligne.isBlank()).map(TrancheImpot::parse).toList();
    }
}

// calculates the tax for each taxpayer and writes the results
int calculerImpots(List<TrancheImpot> tranches, List<String> contribuables, Path sortie) throws IOException {
    try (BufferedWriter ecrivain = Files.newBufferedWriter(sortie)) {
        for (String ligne : contribuables) {
            Matcher champs = CONTRIBUABLE.matcher(ligne.trim());
            String resultat = champs.matches()
                    ? "impôt = " + calculerImpot(tranches, champs.group(1).equals("o"),
                            Integer.parseInt(champs.group(2)), Integer.parseInt(champs.group(3))) + " €"
                    : "ligne incorrecte";
            ecrivain.write(String.format("%-12s : %s", ligne, resultat));
            ecrivain.newLine();
        }
    }
    return contribuables.size();
}

// tax calculation (2004 tax schedule based on 2003 income, retained for the fiscal year)
int calculerImpot(List<TrancheImpot> tranches, boolean marie, int nbEnfants, int salaire) {
    BigDecimal nbParts = BigDecimal.valueOf(nbEnfants).divide(BigDecimal.TWO)
            .add(BigDecimal.valueOf(marie ? 2 : 1));
    if (nbEnfants >= 3) {
        nbParts = nbParts.add(new BigDecimal("0.5"));
    }
    BigDecimal revenu = new BigDecimal("0.72").multiply(BigDecimal.valueOf(salaire));
    BigDecimal quotient = revenu.divide(nbParts, MathContext.DECIMAL64);
     // the first tax bracket whose threshold exceeds the family quotient, otherwise the last one
    TrancheImpot tranche = tranches.stream()
            .filter(t -> quotient.compareTo(t.limite()) <= 0)
            .findFirst()
            .orElse(tranches.getLast());
    return tranche.coeffR().multiply(revenu).subtract(tranche.coeffN().multiply(nbParts)).intValue();
}

// a tax bracket
record TrancheImpot(BigDecimal limite, BigDecimal coeffR, BigDecimal coeffN) {
    static TrancheImpot parse(String ligne) {
        String[] champs = ligne.split(":");
        return new TrancheImpot(new BigDecimal(champs[0]), new BigDecimal(champs[1]),
                new BigDecimal(champs[2]));
    }
}

    9.15. The Golden Rules

    Let’s summarize the rules of asynchronous programming in Java:

    • to wait, do not block a system thread: a wait (I/O, timeout, or other operation) is performed either in a virtual thread or by attaching a continuation to a [CompletableFuture];
    • for new code, prefer virtual threads: write blocking, sequential, and readable code (loops, [try / catch], ordinary local variables), executed by [Executors.newVirtualThreadPerTaskExecutor()]; one virtual thread per task, never use a pool of virtual threads;
    • Use [CompletableFuture] to compose operations, or to use a API that returns [CompletableFuture] ([HttpClient.sendAsync], reactive libraries); We then choose the continuation executor ([xxxAsync(..., executeur)]) and never execute a blocking operation in the shared pool;
    • no [join()] or [get()] in a continuation or in a GUI thread: these waits block the thread executing them. They belong in the main program or in a virtual thread;
    • Virtual threads are used for waits, not computations: for computations, use a platform-specific thread pool sized according to the number of processors, or parallel streams;
    • limit access to scarce resources using a [Semaphore], not by the size of a thread pool;
    • Cancellation is cooperative: a task is canceled via [Future.cancel(true)], which interrupts its thread; an interrupted task terminates gracefully; a [InterruptedException] is never masked (it is either propagated or the interrupt flag is reset). And remember that [CompletableFuture.cancel] does not interrupt anything;
    • limit wait times: [orTimeout], [completeOnTimeout], [get(délai, unité)]; and terminate the operation itself if the wait is abandoned;
    • start first, then wait: to run multiple independent operations simultaneously, start them all and then wait for them ([allOf], [invokeAll], the executor’s [close] method);
    • A launched operation must be waited on or monitored: a forgotten operation hides its exceptions ([exceptionally], [whenComplete] to handle them); by tracing back a [CompletionException] or a [ExecutionException], we seek the root cause.

    7. Functional Interfaces, Lambdas, and Events

    In many programs, we need to pass not data but behavior to a method: the sorting criterion, the filtering condition, or the processing to be performed when something happens. Java addresses this need with a simple concept upon which this entire chapter is based: the functional interface—that is, an interface that declares only a single abstract method. An object that implements such an interface “carries” a function, which can be stored in a variable, passed as a parameter, returned as the result of a method, and executed at will.

    Before Java 8 (2014), you had to write a class—often an anonymous class—for each behavior you wanted to express, which was verbose. Java 8 introduced lambda expressions and method references, which allow you to write this behavior in a single line. We’ve already used them without going into detail with the API Stream in Chapter 5: in [personnes.stream().filter(p -> p.age() >= 18)], we pass a lambda—that is, an instance of a functional interface—to the [filter] method. This chapter explains what lies behind this syntax. It concludes with events, which Java handles using “listeners”: objects—often lambdas—that register with an emitter to be notified of what is happening there. Java graphical user interfaces (Swing, JavaFX) and web frameworks alike rely on this mechanism: a button click or the arrival of a request (HTTP) are signaled to registered listeners. This course does not cover graphical user interfaces; all examples are console programs.

    The programs in this chapter are compact source files located in the [07-lambdas] folder. They are run using [java LambdasNN.java]. Note that a compact source file automatically imports the entire [java.base] module: the interfaces from the [java.util.function], [java.util], or [java.util.concurrent] packages can be used there without any [import] statements.

    7.1. Predefined functional interfaces

    7.1.1. The concept of a functional interface

    A functional interface is an interface that has exactly one abstract method. It may also have as many [default] and [static] methods as desired (see Chapter 4): these do not count. This single abstract method describes a model (also called a signature or form) of a function: the types of its parameters and the type of its return value. A variable of the interface’s type can then refer to any object that provides a function of this form and execute it by calling the method.

    The oldest example is the [java.lang.Runnable] interface, which has existed since Java 1.0 and represents a task to be executed (we’ll revisit it in connection with threads in Chapter 8). It boils down to a single method: [void run();]. It describes a function:

    • with no parameters;
    • returning no result ([void]).

    There are three ways to create an object of type [Runnable]:

    • write a class that implements the interface, either named or anonymous. This was the only way to do it before Java 8;
    • write a lambda expression: [Runnable tache = () -> IO.println("tâche");];
    • write a method reference to an existing method that has the correct form: [Runnable tache = Fonctions::afficher;].

    In the last two cases, the compiler creates the object that implements the interface itself: the lambda or the referenced method becomes the body of the method [run]. The function is then executed by calling the interface method: [tache.run()]. Unlike other languages, Java does not have a specific calling syntax: the interface method is always called by its name ([run], [apply], [test]…).

     // 1 - Runnable: no parameters, no return value: void run()
    Runnable tache = new Runnable() {
        @Override
        public void run() {
            Fonctions.afficher();
        }
    };
     // shorthand form: a method reference

     // 2 - BiFunction<T, U, R>: two parameters, one return value

    IO.println("operation.apply(2, 3)=" + operation.apply(2, 3));
     // Supplier<T>: no parameters, one result
    Supplier<String> saluer = Fonctions::saluer;

    7.2. Defining Your Own Functional Interfaces

    The predefined interfaces are often sufficient, but you can define your own. Simply write an interface with a single abstract method, for example:

    • [interface Operation { int calculer(int n1, int n2); }]

    This interface represents a function that takes two integers and returns an integer. Compared to [IntBinaryOperator], the type [Operation] has a name that describes its purpose, its method has a descriptive name ([calculer] rather than [applyAsInt]), and its parameters have names ([n1], [n2]) that development tools display. It is preceded by the annotation [@FunctionalInterface]: this is not required, but it instructs the compiler to verify that the interface is functional, and it documents the developer’s intent.

    A variable of type [Operation] named [op] references only one function at a time. Unlike other languages, which offer “multicast delegates,” Java does not provide a way to store multiple functions in a single variable and execute them all with a single call: when needed, functions are placed in a list and executed one by one. This is exactly what we will do with event listeners.

     // a variable of type Operation receives the static method increase
    Operation op = Calculs::augmenter;
     // the operation is executed
    int n = op.calculer(4, 7);
    IO.println("n=" + n);

    op = c1::ajouter;

    IO.println("n=" + n);
     // then the `subtract` method of c1
    op = c1::soustraire;
    n = op.calculer(2, 3);
    IO.println("n=" + n);

     // A variable can only reference one function: to execute multiple functions, use a list
    List<Operation> operations = new ArrayList<>();
    operations.add(c1::ajouter);
    operations.add(c1::soustraire);
    operations.add((n1, n2) -> n1 * n2);
    for (Operation operation : operations) {
        IO.println("-> " + operation.calculer(10, 4));
    }

     // A default method of the interface creates a new operation
    Operation sommeAuCarre = ((Operation) c1::ajouter).puis(x -> x * x);

    IO.println("longueur(\"Bonjour\")=" + longueur.transformer("Bonjour"));
    IO.println("etoiles(5)=" + etoiles.transformer(5));

// Definition of a functional interface: a single abstract method
// that takes two integers as parameters and returns an integer
@FunctionalInterface
interface Operation {
    int calculer(int n1, int n2);

     // A default method does not count: the interface remains functional
    default Operation puis(IntUnaryOperator suite) {
        return (n1, n2) -> suite.applyAsInt(calculer(n1, n2));
    }
}

// A generic functional interface: T -> R
@FunctionalInterface
interface Transformation<T, R> {
    R transformer(T valeur);
}

// a class whose methods have the same form as the Operation interface
class Calculs {
     // two instance methods
    int ajouter(int n1, int n2) {
        IO.println("ajouter(" + n1 + "," + n2 + ")");
        return n1 + n2;
    }

    int soustraire(int n1, int n2) {
        IO.println("soustraire(" + n1 + "," + n2 + ")");
        return n1 - n2;
    }

     // a static method
    static int augmenter(int n1, int n2) {
        IO.println("augmenter(" + n1 + "," + n2 + ")");
        return n1 + 2 * n2;
    }
}

void main() {
     // 1 - an anonymous class: the class that implements the interface is written in place
    IntBinaryOperator ajouter = new IntBinaryOperator() {
        @Override
        public int applyAsInt(int n1, int n2) {
            return n1 + n2;
        }
    };
    IO.println("classe anonyme : ajouter(2, 3)=" + ajouter.applyAsInt(2, 3));

     // 2 - the same thing with a lambda expression (Java 8): parameters -> body
    IntBinaryOperator soustraire = (int n1, int n2) -> {
        return n1 - n2;
    };
    IO.println("lambda à corps de bloc : soustraire(2, 3)=" + soustraire.applyAsInt(2, 3));

     // 3 - Parameter types are inferred from the target interface
    IntBinaryOperator multiplier = (n1, n2) -> n1 * n2;
    IO.println("lambda à corps d'expression : multiplier(2, 3)=" + multiplier.applyAsInt(2, 3));

     // 4 - a single parameter: parentheses are optional

    Predicate<String> estVide = s -> s.isEmpty();
    IO.println("carre(7)=" + carre.applyAsInt(7) + ", estVide(\"\")=" + estVide.test(""));

     // 5 - no parameters: empty parentheses
    Supplier<String> saluer = () -> "Bonjour";
    Runnable bip = () -> IO.println("bip !");
    IO.println(saluer.get());
    bip.run();

     // 6 - a block body with multiple statements
    BiConsumer<String, Integer> repeter = (texte, fois) -> {
        for (int i = 0; i < fois; i++) {
            IO.print(texte);
        }
        IO.println();
    };
    repeter.accept("ab", 3);

     // 7 - anonymous parameters (Java 22): their values are not required
    BiConsumer<Object, String> ecouteur = (_, _) -> IO.println("événement reçu");
    ecouteur.accept(null, "clic");

    List<Integer> nombres = new ArrayList<>(List.of(3, 8, 1, 6, 5, 4));
    List<Integer> pairs = new ArrayList<>(nombres);
    pairs.removeIf(n -> n % 2 != 0);
    IO.println("pairs : " + pairs);
    nombres.sort((n1, n2) -> Integer.compare(n2, n1));

    Form
    Example
    typed parameters, block body
    [(int a, int b) -> { return a + b; }]
    untyped parameters, expression body

    a single untyped parameter

    A lambda is not quite the same as a shorthand anonymous class. In an anonymous class, [this] refers to the instance of the anonymous class; in a lambda, [this] refers to the object of the method that encloses the lambda. Furthermore, an anonymous class creates a new scope: it can declare a variable with the same name as a variable in the method, which a lambda cannot do. Finally, an anonymous class can implement an interface with multiple methods or inherit from an abstract class, which is impossible with a lambda. In this course, we will use lambdas whenever possible.

By requiring that variables remain unchanged, Java prevents these situations; when a shared, mutable state is truly necessary, it is made explicit using an object ([AtomicInteger], collection…) whose behavior with respect to threads is specified.

We therefore reserve functional interfaces for short, one-off behaviors (a criterion, a transformation, an action), and “business” interfaces for the application’s roles, regardless of the number of methods they contain.

    7.5. Event Handling

    7.5.1. The Listener Model

    Functional interfaces are used to set up events. Java does not have a dedicated keyword for events: it uses a set of conventions, known as the “listener model,” established as early as Java 1.1 for graphical components and JavaBeans. A class [C1] that wants to signal an event [Xxx] proceeds as follows:

    • A [XxxEvent] class, derived from [java.util.EventObject], encapsulates the event information. [EventObject] stores the object that triggered the event—referred to as the source—which is obtained via [getSource()];
    • an interface [XxxListener], which extends the empty interface [java.util.EventListener] (a simple marker), defines the method(s) that will be called when the event occurs. With a single method, it is a functional interface: a listener can be a lambda;
    • The [C1] class manages a list of listeners and provides two public methods for subscribing to and unsubscribing from it: [addXxxListener(XxxListener l)] and [removeXxxListener(XxxListener l)];
    • When an instance of [c1] (derived from [C1]) wants to signal the event, it creates a [XxxEvent] object and calls the method of each registered listener, passing this object to it. By convention, this notification is handled by a protected method [fireXxx(XxxEvent e)] (“fire”), which a derived class can override to modify how the event is published;
    • if a [c2] object wants to be notified of the [Xxx] event from the [c1] object, it registers itself using [c1.addXxxListener(...)]. It can unsubscribe via [c1.removeXxxListener(...)] when it no longer wishes to be notified. Since [c1] manages a list, different objects can subscribe to be notified of the same event.

    In this scenario, we have:

    • a class that signals (also called “publishes” or “emits”) an event;
    • objects that are notified of this event. They are said to subscribe to or register for the event: these are the listeners, or event handlers;
    • a listener interface that defines the signature of the methods that will be notified of the event.

    This is the Observer design pattern: the emitter does not know its subscribers; it simply notifies them. This model offers the same protection as a dedicated keyword: the list of listeners is a private field of the emitter. From the outside, one can only subscribe or unsubscribe; one cannot clear the list, replace other listeners, or trigger the event in place of the emitter.

    7.6. Lambdas and the API Stream

    In Chapter 5, we used the methods of the API Stream ([filter], [map], [sorted]…) by passing lambda expressions to them. void main() {
    List<Integer> nombres = List.of(3, 8, 1, 6, 5, 4, 9, 2);

    Predicate<Integer> estPair = n -> n % 2 == 0;

    IO.println("filtrer(n > 4) : " + Outils.filtrer(nombres, n -> n > 4));
    IO.println("filtrer(estImpair) : " + Outils.filtrer(nombres, Outils::estImpair));

     // 3 - Execution is deferred: the predicate is only called by the terminal operation
    Stream<Integer> grands = nombres.stream().filter(n -> {
        IO.print("[test " + n + "] ");
        return n > 7;
    });
    IO.println("le flux est défini, rien n'a encore été exécuté");
    grands.forEach(n -> IO.print("-> " + n + " "));
    IO.println();

     // 4 - Our own intermediate operations with intermediate collectors (Gatherer, Java 24)
    List<String> villes = List.of("Angers", "Paris", "Lyon", "Nantes", "Aix");
    List<String> resultat = villes.stream()
            .gather(Outils.filtrer(v -> v.length() <= 5))
            .gather(Outils.transformer(String::toUpperCase))
            .toList();
    IO.println("gatherers : " + resultat);
}

class Outils {
     // filters a list using a predicate: the work performed by the `filter` method
    static <T> List<T> filtrer(List<T> source, Predicate<? super T> predicat) {
        List<T> resultat = new ArrayList<>();
        for (T element : source) {
            if (predicat.test(element)) {
                resultat.add(element);
            }
        }
        return resultat;
    }

    static boolean estImpair(int n) {
        return n % 2 != 0;
    }

     // an intermediate stream operation that only lets through elements that satisfy the predicate
    static <T> Gatherer<T, ?, T> filtrer(Predicate<? super T> predicat) {
        return Gatherer.of((_, element, aval) -> !predicat.test(element) || aval.push(element));
    }

     // an intermediate operation that transforms each element: the equivalent of `map`
    static <T, R> Gatherer<T, ?, R> transformer(Function<? super T, ? extends R> transformation) {
        return Gatherer.of((_, element, aval) -> aval.push(transformation.apply(element)));
    }
}

[Gatherer.of] receives a lambda with three parameters, called for each element in the stream: a state (unnecessary here, hence the anonymous parameter [_]), the element, and the next stage in the flow ([aval]), to which an element is passed via [aval.push(...)]. The lambda returns [false] to stop the stream; our functions never decide this on their own: they return the result of [push], which is equal to [false] only if the downstream component no longer wants any elements (or [true] when the filter discards an element). The filter (line 52) transmits only the elements that satisfy the predicate; the transformation (line 57) transmits the result of the function applied to each element;
    • line 56: [transformer] is doubly generic: [T] is the type of the received elements, and [R] is the type of the produced elements. The parameter [Function<? super T, ? extends R>] follows the rule we’ve already encountered: the function consumes [T] and produces [R];

    The entire API stream is built on this model: operations that receive functional interfaces and produce new streams, whose elements are calculated only upon request by the terminal operation.

    7.7. Expression Trees

    Some languages, such as C#, allow a lambda to be converted not into executable code, but into a data structure that describes it (an “expression tree”): a program can then parse the lambda [t -> t.getLimite() > 20000] and translate it, for example, into a clause SQL [WHERE limite > 20000] executed by the database server.

    Java has no equivalent. A Java lambda is always compiled into executable code: you can call it, but you cannot examine what it does. Database access libraries therefore use other means to express a query. Hibernate, which we will cover in Chapter 11, offers two solutions: a query language similar to SQL but expressed in terms of classes and properties, HQL (["from Tranche t where t.limite > 20000"]), and Jakarta Persistence’s API Criteria, which constructs the query through method calls ([cb.gt(t.get("limite"), 20000)]). In both cases, the query is data (a string or an object tree) that Hibernate translates into SQL, whereas a lambda passed to [filter] is executed within the Java program.

    7.8. Conclusion

    Key takeaways from this chapter:

    • A functional interface is an interface that has only one abstract method. The predefined interfaces in the [java.util.function] package ([Function], [Supplier], [Consumer], [Predicate], their two-parameter variants, and their primitive versions), along with [Runnable], [Callable], and [Comparator], usually eliminate the need to define your own; when one is defined, it is annotated as [@FunctionalInterface];
    • A functional interface can be implemented by a class (named or anonymous), by a lambda expression, or by a method reference ([Classe::statique], [objet::methode], [Classe::methode], [Classe::new]). A lambda has no type of its own: the target type determines it;
    • Lambdas capture the local variables surrounding them, provided that those variables are actually final; mutable state is handled through an object or a field;
    • The methods [andThen], [compose], [and], [negate], [comparing], [thenComparing]… build new functions from existing ones;
    • In Java, a lambda is an instance of an interface: a functional interface is chosen for short, one-time behavior, while an interface with multiple methods (or a “business” interface) is chosen for an application role;
    • an event is set up using the listener pattern: a class [XxxEvent] derived from [EventObject], an interface [XxxListener], methods [addXxxListener] / [removeXxxListener], and a list of listeners ([CopyOnWriteArrayList]) iterated over by a method [fireXxx]. To unsubscribe a listener, you must retain the subscribed object. [PropertyChangeSupport] provides this mechanism out of the box for property changes;
    • the API Stream is built on operations that accept functional interfaces; Java does not have expression trees, and Hibernate expresses its queries in HQL or using the API Criteria.

    Lambdas will reappear in all subsequent chapters: a thread executes a [Runnable], and a [ExecutorService] executes a [Callable] (Chapter 8), a [CompletableFuture] chains functions (Chapter 9), and Spring Boot web services handle HTTP requests in methods that the framework calls as listeners (Chapter 13).
